----------------------------------------------------------------
  WHAT IS THIS PROJECT?
----------------------------------------------------------------

LeetRevision is a personal web application that helps you
remember LeetCode problems you have already solved.

The core idea is simple:
  - You solve a LeetCode problem
  - You log it in this app
  - The app schedules automatic reminders to revise it
    (e.g. after 5 days, 12 days, 30 days, etc.)
  - Every day you open the app and it shows what to revise today

This is based on a learning technique called "Spaced Repetition",
where you review material at increasing intervals so you never
forget it.

----------------------------------------------------------------
  TECHNOLOGY STACK (What tools were used to build it)
----------------------------------------------------------------

1. NEXT.JS (v15+)
   - The main web framework. It handles both the frontend (what
     you see in the browser) and the backend (API routes that
     talk to the database).
   - Built on top of React.js.

2. REACT.JS
   - The UI library. Every button, card, and page is a React
     component - a reusable piece of UI written in TypeScript/JSX.

3. TYPESCRIPT
   - A version of JavaScript with strict data types.
   - Helps catch bugs during coding instead of at runtime.

4. SUPABASE
   - A cloud database and authentication service.
   - The database is PostgreSQL (rows and tables).
   - Supabase handles user sign-up, login, and JWT session tokens.
   - Stores all problems, revision schedules, and user profiles.

5. TAILWIND CSS
   - A utility-first CSS framework used for all styling
     (colors, layout, spacing, animations).

6. TANSTACK REACT QUERY
   - A data-fetching library that caches API responses in memory.
   - Prevents unnecessary repeated calls to the database.
   - Automatically refreshes data when the user takes an action.

7. RESEND (optional)
   - An email delivery API used to send feedback messages
     submitted by users to the developer email inbox.

8. NODE.JS / NPM
   - Node.js is the JavaScript runtime that runs the development
     server on your computer.
   - NPM (Node Package Manager) installs all the above libraries
     from the internet into the project "node_modules" folder.

----------------------------------------------------------------
  HOW TO START THE PROJECT (NPM Setup)
----------------------------------------------------------------

Step 1: Install dependencies
  > npm install
  This reads the "package.json" file and downloads all required
  libraries into a folder called "node_modules".

Step 2: Set environment variables
  A file called ".env.local" holds secret credentials:
    - NEXT_PUBLIC_SUPABASE_URL      -> URL of the cloud database
    - NEXT_PUBLIC_SUPABASE_ANON_KEY -> Public key to connect to DB
    - SUPABASE_SERVICE_ROLE_KEY     -> Admin key (server-side only)
    - RESEND_API_KEY                -> For sending feedback emails
    - FEEDBACK_RECIPIENT_EMAIL      -> Where to deliver emails

Step 3: Run the development server
  > npm run dev
  This starts a local web server at http://localhost:3000

Step 4: Build for production
  > npm run build
  Compiles everything into optimized JavaScript for deployment.

----------------------------------------------------------------
  DATABASE DESIGN (Tables in Supabase/PostgreSQL)
----------------------------------------------------------------

TABLE: auth.users  (managed automatically by Supabase)
  - Stores email, hashed password, and user ID.

TABLE: profiles
  - One row per registered user.
  - Columns:
      display_name             - User's chosen name
      timezone                 - e.g. "Asia/Kolkata"
      leetcode_username        - Connected LeetCode account
      leetcode_session         - Saved session cookie (encrypted)
      default_revision_intervals - e.g. [5, 12, 30]
      leetcode_imported_at     - When last synced from LeetCode

TABLE: problems
  - One row per problem the user has logged.
  - Columns:
      title                    - Problem name
      topic                    - e.g. "Arrays", "Dynamic Programming"
      priority                 - "low", "medium", or "high"
      problem_link             - URL to LeetCode problem
      date_solved              - When the user solved it
      revision_intervals       - e.g. [5, 12, 30] (days)
      solutions                - JSON storing code (brute/better/optimal)
      source                   - "manual" or "leetcode_import"
      leetcode_slug            - Short name used in LeetCode URL

TABLE: revision_entries
  - One row per scheduled revision for each problem.
  - Columns:
      problem_id               - Links to problems table
      scheduled_date           - When to revise (YYYY-MM-DD)
      interval_days            - 5, 12, 30, etc.
      interval_label           - "5-day", "12-day", etc.
      status                   - "pending", "done", or "missed"
      completed_date           - When user marked it done

  EXAMPLE: You solve "Two Sum" today (2026-01-01), intervals=[5,12]
    Row 1: scheduled=2026-01-06, interval=5,  status=pending
    Row 2: scheduled=2026-01-13, interval=12, status=pending

    You mark Row 1 done on 2026-01-06:
      -> Row 1: status=done, completed_date=2026-01-06
      -> NEW Row 1 created: scheduled=2026-01-11, status=pending

TABLE: feedback
  - Stores user feedback submissions.
  - Columns: user_id, user_email, subject, message, category

Row Level Security (RLS):
  - A database-level rule that makes it IMPOSSIBLE for one user
    to read or change another user's rows, even if they try
    to craft a malicious query. Enforced by Supabase itself.

----------------------------------------------------------------
  AUTHENTICATION (How Login Works Step by Step)
----------------------------------------------------------------

1. User visits any page.
   -> middleware.ts intercepts the request.
   -> It checks if a valid session cookie exists in the browser.

2. No valid session found:
   -> User is automatically redirected to /login.

3. User enters email and password on /login.
   -> Supabase checks the credentials against auth.users table.
   -> If correct, Supabase creates a JWT (JSON Web Token).
   -> The JWT is stored as an httpOnly cookie in the browser.

4. On every subsequent page visit:
   -> The cookie is sent automatically with the request.
   -> middleware.ts verifies the JWT with Supabase.
   -> Supabase returns the user's unique ID.
   -> All DB queries are filtered by that user ID.

5. Sign out:
   -> Supabase clears the cookie.
   -> User is redirected back to /login.

WHAT IS A JWT?
  A JSON Web Token is a small encrypted string like:
    eyJhbGciOiJIUzI1NiIsInR5cCI6IkpXVCJ9...
  It contains your user ID and an expiry time, digitally
  signed by Supabase. It CANNOT be faked or tampered with.

WHAT IS httpOnly?
  A cookie flag that prevents JavaScript running in the browser
  from reading the cookie. This protects against XSS attacks
  (where a hacker tries to steal your session via JS).

----------------------------------------------------------------
  HOW THE REVISION SCHEDULING SYSTEM WORKS
----------------------------------------------------------------

STEP 1 - User adds a problem
  Form inputs: title, topic, priority, date solved,
               revision intervals (e.g. [5, 12, 30])

  App creates:
    - 1 row in "problems" table
    - N rows in "revision_entries" (one per interval), status=pending

STEP 2 - Daily queue (Home page)
  Query runs: SELECT from revision_entries WHERE
    status IN ('pending', 'missed')
    AND scheduled_date <= today (in user's timezone)

  This gives the list of problems due today.
  Past-due entries get their status changed to "missed".

STEP 3 - Marking a revision as done
  User clicks "Done" button.
  App does:
    - UPDATE revision_entries SET status='done', completed_date=today
    - INSERT new revision_entry: scheduled = old_scheduled + interval

  KEY DESIGN CHOICE: The next scheduled date is calculated from
  the ORIGINAL scheduled date, not today's date.
  Example: Scheduled for Jan 6, done on Jan 8 (2 days late)
    -> Next scheduled = Jan 6 + 5 = Jan 11 (NOT Jan 8 + 5 = Jan 13)
  This keeps the revision cadence consistent even if you are late.

STEP 4 - Editing a problem
  If user changes intervals or solved date:
    - All pending/missed entries for that problem are DELETED
    - New entries are re-seeded based on new intervals
  This prevents stale or orphaned revision entries.

STEP 5 - Turning off revision (Pause Problem)
  In the add/edit form, checking "Turn off revision for this problem":
    - Sets revision_disabled = true in DB
    - Deletes all pending/missed revision entries for this problem
    - The problem no longer appears in daily revision queue
    - The revised retention graph (% revised) automatically excludes
      this problem from the total denominator so stats stay accurate

STREAK TRACKING (Current & Longest Streak)
  - Active Date: Any calendar day where the user completed at least
    one revision OR solved/added at least 1 problem. Solving just 1
    problem increments the streak by 1.
  - Rest / Exempt Day: Any calendar day where 0 revisions were due.
    Rest days do NOT break your streak — the streak bridges across
    rest days seamlessly.
  - Missed Day: A past calendar day where revisions were due but left
    uncompleted with 0 activity. Missed days reset the active streak.
  - Current Streak (Flame 🔥 on Home Page): Active streak up to today.
  - Longest Streak (Trophy 🏆 on Profile Page): Maximum consecutive
    streak achieved.

----------------------------------------------------------------
  LEETCODE INTEGRATION (Importing Your Solved Problems)
----------------------------------------------------------------

PURPOSE:
  Instead of typing every LeetCode problem manually, users can
  import all their solved problems with one click.

HOW THE COOKIE IMPORT WORKS:

  1. User opens LeetCode in browser and logs in.

  2. User presses F12 to open Developer Tools.
     Goes to: Application tab -> Cookies -> leetcode.com
     Finds "LEETCODE_SESSION" and copies the value.

  3. User pastes the cookie value into the Profile page
     and clicks "Save & Sync All Problems".

  4. App sends an authenticated POST request to LeetCode
     using the cookie in the HTTP header.
     The cookie proves the user is logged in — no username
     or external API key is needed.

  5. LeetCode returns all problems where status = "AC"
     (Accepted = successfully solved).

  6. The app fetches ALL existing problems from the DB in
     ONE single batch query (not one per problem).
     It compares titles/slugs to find only NEW ones.

  7. New problems are inserted in batches of 50 at a time.
     Revision entries are seeded for each one automatically.

  8. The cookie is saved to the user's profile in Supabase
     so next time they can sync with ONE CLICK.

ERROR HANDLING:
  - Wrong/expired cookie   -> error: "Invalid LEETCODE_SESSION cookie"
  - No solved problems     -> message: "No accepted solved problems found"
  - Network failure        -> error is caught and shown to user

BULK PASTE IMPORT (No cookie needed):
  User pastes a plain text list of problem names (one per line).
  The server splits by newline and creates a problem for each one.

----------------------------------------------------------------
  ALL API ROUTES (Backend Endpoints)
----------------------------------------------------------------

These run on the server (not in the browser). Secrets are safe.

GET  /api/profile
  -> Reads the current user's profile from Supabase
  -> Returns: display_name, timezone, intervals, cookie status

PATCH /api/profile
  -> Updates profile fields (name, timezone, intervals, etc.)

POST /api/leetcode/import
  -> Uses session cookie to fetch all solved problems from LeetCode
  -> Batch-deduplicates and inserts new problems into DB
  -> Seeds revision entries for each new problem
  -> Saves the cookie to profile for future 1-click syncs

POST /api/leetcode/bulk-import
  -> Accepts a raw text list of problem names
  -> Parses and inserts them into DB with revision seeds

GET  /api/leetcode?username=xxx
  -> Fetches PUBLIC stats from LeetCode's GraphQL (no auth needed)
  -> Returns: total solved, easy count, medium count, hard count
  -> Used by the Profile page "Connect" button

POST /api/leetcode/signout
  -> Removes LeetCode username and saved cookie from profile
  -> Option to also delete all leetcode_imported problems

POST /api/feedback
  -> Inserts the feedback row into Supabase "feedback" table
  -> Logs the message with all details to server console
  -> If RESEND_API_KEY is set, sends an email to the developer

POST /api/reminders/send
  -> Checks user profile for email_reminders_enabled (default true)
  -> Fetches due revisions for today in user's timezone
  -> SKIPS sending if 0 problems due for revision today
  -> Sends email: "Let the streak number only go up. Here is your
     reminder for daily revision" with link to today's revision queue

DELETE /api/account/delete
  -> Permanently deletes all revision entries, problems, feedback,
     profile settings, and the auth user account from Supabase.

----------------------------------------------------------------
  THE SCHEDULING ALGORITHM (src/lib/scheduling.ts)
----------------------------------------------------------------

This file is the mathematical brain of the app.

seedRevisionsFromSolved(dateSolved, intervals)
  Input:  dateSolved = "2026-01-01", intervals = [5, 12, 30]
  Output:
    { scheduled_date: "2026-01-06", interval_days: 5,  label: "5-day"  }
    { scheduled_date: "2026-01-13", interval_days: 12, label: "12-day" }
    { scheduled_date: "2026-01-31", interval_days: 30, label: "30-day" }

nextRevisionAfterComplete(scheduledDate, intervalDays)
  Input:  scheduled = "2026-01-06", interval = 5
  Output: { scheduled_date: "2026-01-11", interval_days: 5 }
  (Always adds to the SCHEDULED date to keep cadence consistent)

formatNextRevision(scheduledDate, today)
  "today"              if due today
  "in 3 days"          if upcoming
  "overdue by 2 days"  if past due

todayInTimezone(timezone)
  Returns the current date in the user's local timezone.
  e.g. For "Asia/Kolkata" (IST +5:30), returns Indian local date.

isOverdue(scheduledDate, today)
  Returns true if scheduled date is in the past.
  Used to mark entries "missed" and show warning badges.

----------------------------------------------------------------
  SECURITY FEATURES
----------------------------------------------------------------

1. Row Level Security (RLS) in Supabase
   - Enforced AT THE DATABASE LEVEL, not just in app code
   - Users can only SELECT/INSERT/UPDATE their OWN rows
   - If someone bypasses the frontend, the DB still blocks them

2. Server-Side Secrets
   - SUPABASE_SERVICE_ROLE_KEY never leaves the server
   - The browser only ever sees the public anon key
   - RLS makes the anon key safe to expose publicly

3. httpOnly Cookie for Sessions
   - Browser JavaScript CANNOT read the session cookie
   - Prevents XSS (Cross-Site Scripting) cookie theft attacks

4. LeetCode Cookie Stored Securely
   - Saved in Supabase DB row, not in browser localStorage
   - Accessible only via authenticated server-side API calls
   - Never exposed in any API response to the browser

5. Environment Variables in .gitignore
   - .env.local is listed in .gitignore
   - Secret keys are NEVER uploaded to GitHub or any public repo

6. Input Sanitization
   - All text fields are .trim()-ed before DB insert
   - Supabase parameterized queries prevent SQL injection

----------------------------------------------------------------
  PERFORMANCE OPTIMIZATIONS APPLIED
----------------------------------------------------------------

1. React Query Caching
   - Fetched data is kept in memory
   - Navigation between pages does not re-call the database

2. Stable Query Keys (Bug Fix)
   - Originally used raw arrays as query keys which caused
     infinite re-fetch loops (new array reference each render)
   - Fixed: array of IDs is joined to a stable string key

3. Batch Import (Major Optimization)
   - Old code: 1 DB SELECT + 1 DB INSERT per problem (N*2 queries)
   - New code: 1 batch SELECT for all slugs + 1 bulk INSERT (50/chunk)
   - For 500 problems: reduced from 1000+ queries to about 14

4. Paginated LeetCode Fetch
   - Fetches 100 problems per GraphQL call, loops until all are done
   - Handles accounts with 500+ solved problems correctly
